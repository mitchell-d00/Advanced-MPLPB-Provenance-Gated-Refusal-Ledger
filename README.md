# Advanced MPLPB — JavaScript project API hub

**Version 0.3.0 · project API hub · provenance-gated console**

**[Open Advanced MPLPB](https://mitchell-d00.github.io/Advanced-MPLPB-Provenance-Gated-Refusal-Ledger/)**: it runs entirely in your browser, with no account, API key or server.

Advanced MPLPB brings **Combined MPLPB, Mitchell Tech and Pendulums** into one
browser-local JavaScript hub, usable on the live site or localhost. Run their
bundled APIs, inspect deployment assets, retain test evidence and follow the same
release checklist across projects: current docs, automated tests, browser checks
and deployment verification.

The **Project API hub** provides project/live/CI links, a JSON playground,
individual/all-project smoke checks and evidence-required release checklists.
The existing **Evidence console** retains strict source gates, calculator and
conservation checks, and an exportable hash-linked refusal ledger. Composition
requires a supported source answer; page retrieval alone cannot unlock it.

```js
await AdvancedMPLPBHub.ready();
await AdvancedMPLPBHub.call('calculator','calculate',['sin(pi/2)+2^3']);
await AdvancedMPLPBHub.checkAll();
await AdvancedMPLPBHub.checkDeployment('pendulums');
AdvancedMPLPBHub.exportReport();
```

Read the [hub API guide](docs/HUB_API.md) for adapters, local deployment URLs,
check scope and export formats. API calls execute the pinned bundled engines.
Deployment probes explicitly fetch a chosen project's asset; they report HTTP
status and hashes, rather than claiming to execute that remote API.

> One owner returns. Two owners stop. No owner refuses.

## Why this is a separate project

Each of the three projects stands alone and knows nothing about the others.
Advanced MPLPB is the layer that connects them. It changes none of them, and
adds what does not belong in any one of them:

- **It adds an API and release hub.** Three fixed adapters, a JSON playground,
  deployment probes and per-project evidence checklists work in the hosted app
  and localhost.
- **It adds a cross-engine gate.** Composed calculator and physics work can only start
  from an MPLPB answer that is supported, with intact source identity and quoted
  body evidence. Neither the calculator nor the pendulum sandbox has a notion of
  source authority, and MPLPB has no notion of numeric or dynamic checks.
- **It enforces the split between two contracts.** *Retrieve page* returns a
  cited page marked `answer_supported:false`. *Supported answer* requires source
  support. Only the second can unlock composition, and the console checks source
  identity and quoted evidence again at its own gate.
- **It keeps one ledger across all three engines.** Receipts for retrievals,
  refusals, calculations, conservation checks and kill tests are hash-linked
  in a single exportable session.
- **It pins exact versions.** Upstream repositories keep changing. This repo
  freezes the commits above and verifies the shipped files by SHA-256, so the
  measured results stay reproducible.

## The retrieval repair (now in Combined MPLPB)

The repair was developed here in 0.2.0 and merged into Combined MPLPB as
[pull request #18](https://github.com/mitchell-d00/Combined-MPLPB-A-closed-local-ledger-of-pages-that-answers-only-from-those-pages/pull/18)
(commit `d2f92a8`). It now lives only there. This repository uses it unchanged,
and Combined MPLPB's own `tests/test_page_retrieval.py` holds its tests.


Version 0.1 scored 20/56 because its console sent the historical
**page-retrieval** benchmark through MPLPB's narrower **supported-answer** API.
That was an integration error. The unmodified legacy retrieval reader scores
50/56 on the same questions, which matches the upstream record.

Version 0.2.0 fixed the integration and the reader itself:

1. A discourse wrapper such as “what does it mean if …” no longer adds the
   irrelevant word “mean” to the page lookup. Quantities, polarity, subjects and
   modifiers are kept.
2. When majority-scope and full-prose matching find no owner, a complete
   multi-term `when-to-use` situation clause can select the page that declares it.
   All matching owners are kept. There is no ranking, synonym generation, external
   source, probe-ID lookup or answer synthesis.
3. Generic-topic matches refuse when their proposed owners leave out a requested
   term that eligible pages explicitly exclude. This is not a global ban: a real
   owner of that term can still claim it.
4. A new `MPLPB.retrieve` API checks the selected page against the existing
   provenance gate. If the page is rejected, retrieval stops rather than choosing
   another owner.
5. The console separates **Retrieve page** from **Supported answer**.

The corpus, all 56 questions, expected owner IDs, frozen hashes and existing test
assertions were not changed to get this result.

| Adjacent historical 20 | 10/20 | 15/20 | **16/20** |

## Use it

**Online:** open the [live site](https://mitchell-d00.github.io/Advanced-MPLPB-Provenance-Gated-Refusal-Ledger/).
It loads the full engine, about 37 MB, at startup. Computation then runs in the
browser tab. A warmed tab can query locally without network access; offline
reload is not guaranteed, and there is no service worker or installable offline
package.

**Locally:** clone the repository and serve `web/`:

```sh
python -m http.server 8000 --directory web
```

Then open http://localhost:8000. Opening `web/index.html` directly as a file
does not work, because the split runtime is loaded with local `fetch` requests.
Use HTTPS hosting or localhost. You need WebAssembly, Web Workers, IndexedDB,
Web Locks, local storage and Web Crypto. Keep only one MPLPB runtime open per
origin and browser profile: the hidden engine holds the upstream single-writer
lock. Close another Advanced/Combined MPLPB tab on that origin if startup stops.

Start with the [user guide](docs/USER_GUIDE.md), including the five console modes,
delivery profiles and ledger export limits. The [documentation index](docs/README.md)
lists operational and historical guides.

**From code or an AI agent:** use `window.AdvancedMPLPB` in the open page:

```js
await AdvancedMPLPB.ready();
await AdvancedMPLPB.retrieve('what does it mean if the guard has gone over', {corpus:'studio', profile:'internal'});
await AdvancedMPLPB.query('What is Dungeons and Dragons?', {corpus:'logic', profile:'internal'});
await AdvancedMPLPB.calculate('sin(pi/2)+2^3');
await AdvancedMPLPB.checkDynamics({duration:10, damping:0});
AdvancedMPLPB.exportSession();
```

This is a page-local JavaScript API, not a network service. See
[docs/AGENT_API.md](docs/AGENT_API.md).

## Test and rebuild

Requires Python 3.10+ and Node.js 18+. CI uses Python 3.13 and Node 22.

```sh
python scripts/test.py            # non-browser composition, integration, upstream retrieval and Node suites
python scripts/test.py --full     # adds all 674 upstream MPLPB Python tests (several minutes)
python scripts/verify_assets.py   # SHA-256 check of every file in web/ and src/
python scripts/evaluate_retrieval.py --output evaluation/current-retrieval.json
```

Every push and pull request runs `test.py` and `verify_assets.py` in GitHub
Actions (**Composition regression checks**). Its separate Chromium job installs
Playwright and the matching browser, then checks both the candidate console and
the deployed site. See [testing and evidence](docs/TESTING.md) for exact scope
and current results. Both candidate-hub and deployed-console Chromium checks
passed in [run 40887912028](https://github.com/mitchell-d00/Advanced-MPLPB-Provenance-Gated-Refusal-Ledger/actions/runs/40887912028);
pre-merge deployment testing observes the old live version.

Running the upstream Mitchell Tech suites rewrites their result files under
`upstream/MitchellTech/tests/`, with last-digit floating-point differences.
Review those changes and restore only generated reports before committing; see
[development](docs/DEVELOPMENT.md). Do not reset the whole tests directory if it
contains intentional work.

Browser-only upstream suites need their own Playwright/Chromium setup. The new
`node tests/browser.cjs` checks this combined console. The Node integration test
runs the real Python bridge, calculator code and physics engine with a stubbed
DOM; its results alone do not test rendering or browser storage.

To rebuild `web/` from `upstream/` (the result matches the committed files):

```sh
python scripts/build.py                                   # downloads the hash-pinned Pyodide 314.0.7 core
python scripts/build.py --core-archive pyodide-core-314.0.7.tar.bz2   # offline
python scripts/update_assets.py                           # record new hashes after an intentional change
node scripts/test_wasm.mjs /path/to/extracted/pyodide evaluation/current-wasm.json
```

## Website

GitHub Pages publishes this repository from **main / (root)**, as Pendulums
does, and redeploys on every push. The root [`index.html`](index.html) forwards
to the app in `web/`, and `.nojekyll` makes Pages serve every file as-is.

Alternatively, set **Settings → Pages → Source: GitHub Actions** and run the
**Publish GitHub Pages manually** workflow. It publishes `web/` itself as the
site root, without rebuilding anything.

## Limits

- Retrieval does not prove semantic support, source truth or authorship. Composition
  still requires a supported source answer before calculator or physics work.
- The bundled Dungeons & Dragons example exercises control flow and independent
  numeric checks. It is not a scientific link between a game definition and
  pendulum dynamics.
- The ledger is browser-local and exportable, not a shared or externally signed
  log. A same-origin script can rewrite local storage. Hash chains show byte
  consistency, not who created the content. Browser quota and the 2,000-record
  cap limit storage, so export significant runs.
- Browser validation scope and current results are recorded in
  [docs/VALIDATION.md](docs/VALIDATION.md). Chromium checks do not establish
  cross-browser compatibility, cross-origin CORS behavior or independent human
  performance. Evaluation protocols are in `web/protocols/`.
